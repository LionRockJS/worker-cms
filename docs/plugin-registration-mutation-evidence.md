# Durable plugin registration evidence — 3 November 2026

The optional plugins feature now commits host registry mutations and their exact classified audit receipt in one private-D1 transaction. Implementation is in `src/features/plugins/registration-evidence.ts`, called by `src/features/plugins/routes/manage.ts`. This continues the [locale/message slice](locale-message-mutation-evidence.md); it does not complete W4b.

## Covered local operations

| Operation | Durable outcome |
|---|---|
| Register | New numeric ID, stable registry UUID, generated credential and `plugin.create`. |
| Edit | Label, URL, enabled flag, configuration and sort order with `plugin.update`. |
| Enable/disable | Only the enabled column and timestamp with `plugin.toggle`. |
| Rotate credential | Only the secret column and timestamp with `plugin.rotate_secret`. |
| Unregister | Registry removal, selected stored identity pin and its bounded local approval/state cleanup with `plugin.delete`. |

Evidence targets the registry UUID and records the numeric ID, operation correlation, changed field names and enabled booleans where relevant. Labels, URLs/query strings, configuration values, credentials and credential hashes are excluded. The complete registry and identity snapshots remain private transaction inputs; they are not copied into audit details. Credentials are generated by the existing secure generator, including on registration; submitted secret fields cannot supply the generated credential.

URL edits preserve the credential, pin and existing approvals and reset `cmsTrustedUi` to false, preserving the prior route behavior. This local edit does not reapprove changed remote content. Ordinary edits and toggles do not write the secret column. Unchanged submissions validate the captured state without a new timestamp or mutation event. Duplicate URLs retain the existing friendly validation response; a concurrent registration or stale snapshot refuses rather than reporting success.

## Transaction and classification contract

Admission and completion check the current account/session, `plugin:manage`, complete role/grant catalogue and classification generation. The complete registry and identity snapshots are guarded against concurrent changes. Evidence takes the highest effective registry/identity table and captured pinned-plugin scope classification; unregister also includes the cleanup tables. Protected source reads are awaited, and pending strict request reads are flushed before mutation.

Each source snapshot is bounded to 5,000 rows and 1,000,000 UTF-8 JSON bytes, checked in SQL before returning values to the Worker. Planned states and complete manifests also have byte bounds. Unsafe numeric identities, unsafe legacy pins, absent required schema or oversized catalogues fail closed; remediation requires a reviewed bounded writer rather than truncation.

Exact statement counts, receipt identity/content, preserved creation metadata, transaction-time update bounds and complete final registry/pin state are asserted in the same batch. Missing, ignored or rewritten business/audit writes and trigger-induced authority/policy changes roll back that batch. The saved record is selected within the batch. Both successful and uncertain outcomes invalidate this isolate's manifest/effective-configuration caches; other isolates retain their existing cache behavior.

Unavailable storage, evidence or guard outcomes return `plugin_registration_change_unavailable`, 503/no-store, with coarse incomplete monitoring attempted without source values. A lost acknowledgment can occur after commit: no automatic replay or rollback claim is made. General receipt lookup, durable request idempotency and reconciliation remain R5. Regulated business-write containment remains enforced.

## Unregister boundaries

Cleanup uses only the captured local identity pin, with no remote manifest fetch or first-use identity claim. A pinned unregister snapshots and explicitly deletes that namespace's asset approvals, page-type approvals, file-prefix approvals and plugin state before removing the pin and registry row. Evidence contains complete per-table counts and numeric approval IDs; state keys and the manifest identity use SHA-256 fingerprints. Full preconditions and final emptiness checks reject skipped cleanup or newly inserted namespace rows within the transaction. Other namespaces remain intact.

Sequence counters and limit/pricing settings are deliberately retained, matching existing deletion semantics, and the receipt explicitly records that retention. An unpinned registry row removes only the registry row and records `no_pinned_identity`; it does not infer ownership from a live URL. Unknown orphan namespaces need separate reviewed reconciliation. This contract does not prevent an unmigrated in-flight plugin-state writer from recreating state after unregister; current service authority and lifecycle checks remain R3.

Local credential rotation commits before existing remote resolution and optional tenant enrollment. A failed local transaction cannot start that enrollment. A subsequent remote failure can coexist with a committed rotation; external intent/delivery/recovery evidence remains R4/R5. The subsequent [explicit identity/capability approval slice](plugin-approval-mutation-evidence.md) now covers identity reapproval and asset/file/page-type approval writers. Tenant configuration, connect/disconnect, automatic first-use identity claims, limits/prices and financial administration retain their separate outstanding contracts. DB-only legacy store helpers are not converted into a general actor/evidence service by this slice.
