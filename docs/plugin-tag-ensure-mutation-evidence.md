# Durable contributor tag provisioning — 4 November 2026

This continues W4b/R3 after contributor deletion on `c58dd4d`, integrated with W13/W14 and the independent dashboard fix on baseline `b7089c6`. `POST /__cms/tags/ensure` now plans its bounded find-or-create request and commits all accepted tag creations, exact reuse decisions and receipts in one private-D1 transaction. It preserves the `tags`/indexed `errors` response and separate catalogue publication. This completes this local producer, not W4b or general external recovery.

## Authority and bounded decisions

The route captures a tag-ensure-specific proof before parsing the body, reusing the contributor credential/page-write-grant authority builder. The existing contract requires at least one current approved, manifest-declared page write scope to provision tags across existing taxonomies. This does not introduce a taxonomy-administration grant or permit editing/deleting existing tags. Read-only approval cannot authorize provisioning. Stable registry ID/UUID, enabled URL binding, stored/resolved/inbound credential, exact manifest pin, declared/approved write grants, classification generation and registry lifecycle receipt witness remain checked through the local commit. A proof for another producer cannot authorize this service.

The principal is `plugin:<registry UUID>` with null CMS user, roles and session. Acting-user headers remain explicitly unverified assertions, never an authenticated user. Source/result reads and catalogue publication use the same verified service principal.

At most 200 input entries are accepted. Empty names and unknown taxonomies retain their indexed validation errors; accepted duplicate pairs return the same identity for each input position. Names and taxonomy slugs retain trimming and exact case-sensitive matching. Pair keys are structured tuples. Legacy duplicate stored names are left intact; the lowest existing ID is selected deterministically, with the entire matching set guarded. Reuse does not update the tag or claim a new creation.

The producer loads only requested taxonomy rows, matching tag rows and relevant global slug namespaces. Full matching tags, including lect, and taxonomy metadata have bounded snapshots (5,000 rows / 1 MB each). Slug-owner metadata includes taxonomy identity for classification. Slug generation retains the taxonomy slug/name prefix, normalized-name fallback and numeric suffixes, including collisions among new rows in the same request. Namespace scans and suffix planning are bounded; oversized catalogs/snapshots refuse before insertion rather than looping indefinitely. These are engineering bounds, not evidence of deployed/free-plan capacity.

Source reads are awaited before mutation. Evidence classification takes the maximum of credential/plugin/table policy, requested taxonomy protection, retained taxonomy floors and the taxonomy protection of observed slug owners, even owners in another taxonomy. Evidence contains fingerprints, internal identities, input indices and error codes; it excludes names, slugs, lect, raw request pairs, credentials, labels and configuration values.

## Atomic local receipts

All accepted creations share a transaction with one `tag.create` receipt per unique new pair, one `tag.ensure` receipt per unique reused pair and a `tag.ensure.batch` operation manifest. Per-tag receipts carry taxonomy ID/UUID and all corresponding input indices. The batch manifest records created/reused UUIDs and exact indexed errors. A request containing only invalid entries still requires its decision manifest; an empty request is a guarded no-op without invented mutation receipts. A write-scope refusal requires an exact classified `tag.ensure` denial before a normal 403.

The transaction rechecks taxonomy existence/metadata, exact matching tag sets, slug owners, current authority and policy. A taxonomy appearing after an unknown-taxonomy decision, a concurrently created name match, metadata/body changes, slug claims or revoked credentials/grants refuse the captured plan. No concurrent object is silently adopted mid-transaction. All valid entries commit together or roll back; validation errors remain explicit item decisions.

New IDs advance above the transaction-time tag maximum/time floor. Postconditions require safe positive integer IDs, exact UUID/content/taxonomy/slug/default values and timestamp bounds. Existing tags remain exact, including IDs and bodies. New tags must have no unexpected draft/trash associations or child tags. The optional trash association table is used only when present, with presence guarded. Final checks reverify every receipt after all writes, so ignored inserts, removed/rewritten receipts and later triggers corrupting earlier tags/receipts cannot report success. The obsolete raw per-tag ensure helper has no remaining caller and was removed.

## Uncertainty and external effects

The batch receipt is the local operation manifest; no independent credit reservation or other pre-commit effect requires a separate durable intent phase. A rejected SQLite transaction or failure before the write batch records `not_committed` when error evidence remains available. A lost acknowledgment records `unknown`, retains whatever tags and receipts committed and never replays the business transaction. An error after acknowledged local success records `committed`. Error logging itself is best effort during an outage.

A repeated HTTP ensure request normally resolves the same current pair identities and emits reuse receipts. It is a new operation, not durable request-key idempotency: renames/deletion between requests and unknown-result reconciliation remain R5 work. No automatic uncertain-result retry or compensation is added.

Catalogue publication still runs after local acknowledgment through the existing publish machinery, including reused IDs, with the verified service actor. Local receipts explicitly identify publication as a separate effect and cannot certify destination delivery or undo committed tags on a later failure. Durable external completion/recovery remains R4. No new tag hook, billing action, schema migration or regulated-write exception is introduced.
