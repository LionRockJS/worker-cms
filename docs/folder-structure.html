What each folder is for

Everything in this repository exists to produce one thing: dist/, the compiled Worker and the views it serves. Some folders are built into it; the rest help you ship it safely: the database changes, the checks, the scripts and the reading.

Becomes part of dist/ Works on it, but is never shipped

Pick a role above to bring forward the folders you work in; the rest fade back.

Server admin: you set up, configure and deploy a site. You work with the configuration, the databases and the scripts, and rarely open the source. dist/ is built for you.

Your path

  1. New site: npm run setup writes this clone's wrangler.toml and .dev.vars, can apply the migrations, then builds dist/ and makes the first deploy.
  2. Choose features in cms.features.json, then npm run build.
  3. Migrate first: npx wrangler d1 migrations apply <db> --remote for the CMS database and the published one, plus any migrations/manual/ file a release calls for.
  4. Deploy: npm run deploy -- -c wrangler.production.toml. It type-checks and tests, then deploys the committed, pushed revision.

Watch out

  • New code on an old database fails: migrations always go before deploy.
  • No need to open dist/: setup and deploy rebuild it every time.
  • Turning a feature off stops creating its tables; it never drops the ones already there.

Designer: you change how the admin looks and reads: layout, sections, wording and styles. Your work ends up in dist/views.

Your path

  1. Screens: Liquid files in src/core/views/ (layout, sections, snippets, templates); a feature's own screens in src/features/<id>/views/.
  2. Wording: …/views/locales, one file per language.
  3. Styles: Tailwind classes in the views; shared CSS in assets-source/admin.css.
  4. See it: npm run dev rebuilds, then runs the CMS locally.

Watch out

  • Tailwind keeps only classes it finds in the views. Rebuild after adding one, or it is silently missing.
  • Views escape text for you: use | raw for trusted HTML, and never add | escape.
  • Edit the sources; dist/views is overwritten on every build.

Contributor: you change how the CMS behaves: routes, features, data and search. You work in the source, and prove each change with a test.

Your path

  1. Read first: the docs/ page for the area you are changing.
  2. Code: src/core/ for what is always installed, src/features/<id>/ for an optional feature.
  3. New table or column: the schema.sql beside the code; npm run build regenerates migrations/. Databases already installed need an additive migration.
  4. Prove it: add a test in test/, then npm run type-check and npm test.

Watch out

  • Features never import each other; they cooperate through the generated registries. npm test checks this.
  • Never edit src/generated/ or dist/; the build writes them.
  • A new development script goes in tools/, with an npm run entry.

Folder by folder

Edit the sources; never edit dist/ by hand.

The centre
dist/

The compiled Worker

What actually runs on Cloudflare. It is generated by the build, not committed, and rebuilt every time, so any change made here is lost.

  • worker/index.jsthe Worker code: src/ and dictionary/ bundled into one file
  • views/layout, sections, snippets, templates and locales, served by the Worker
  • views/assets/CSS, JS and icons the browser downloads
Output · do not edit
Built into dist
src/

Source code

The TypeScript the Worker is built from. Start at index.ts.

  • core/always installed: auth, database, pages, publish, rendering
  • features/<id>/optional features, switched on or off in cms.features.json
  • routes/admin and login routes
  • generated/registries written by the build; do not edit
→ dist/worker/index.js
src/core/views · src/features/*/views

The views

Liquid sections, templates, snippets and locale strings live next to the code they belong to. The build merges core's views with the views of each enabled feature, so a feature that is switched off leaves nothing behind.

→ dist/views/ · npm run build:views
assets-source/

Browser assets that need a build

Tailwind CSS and scripts that import npm packages, such as the rich-text editor. They are kept out of the view tree because everything in dist/views/assets is published.

  • admin.cssTailwind → admin.css
  • richtext-md.jsesbuild → one self-contained file
  • yjs.jsesbuild → collaborative editing

Small scripts with no imports can go straight into a views/assets folder instead.

→ dist/views/assets/ · npm run build:css, build:js
dictionary/

Search matching data

Lookup tables for search, so a search in Simplified Chinese also finds Traditional text and the other way round. Generated from the OpenCC dictionaries and read by src/core/db/chinese.ts.

→ bundled into dist/worker/index.js
Around the build · never shipped
migrations/

Database changes

SQL that brings the D1 databases up to what the new code expects. Run it before you deploy: new code on an old database fails.

  • 0001_…sqlthe admin database baseline, built from src/**/schema.sql
  • 000N_enable_…sqladds a feature's tables to an existing database
  • published/the published (public) database
  • manual/one-off changes for databases installed earlier
Step 1 of a deploy
npm run db:migrate (local)
test/

Checks that an update is correct

Vitest tests that run inside the Workers runtime against a real D1. npm test builds first, then also checks that generated files are current and features stay independent.

Before every commit
npm test
tools/

Development scripts

The Node scripts behind the npm run commands. Run them through npm rather than directly.

  • build-*.mjsassemble features, migrations and views
  • check-*.mjsguards run by npm test and CI
  • install.mjsfirst-time setup of a new site
  • migrate-local.mjsapply migrations locally
  • deploy.mjsgated deploy of a committed, pushed revision

How dist/ is built

npm run build runs these in order.

  1. build:version

    git → src/generated/build-info.ts

  2. build:features

    cms.features.json + src/features/* → src/generated/*

  3. build:migrations

    src/**/schema.sql → migrations/0001_initial_schema.sql

  4. build:views

    src/core/views + src/features/<enabled>/views → dist/views

  5. build:css

    assets-source/admin.css → dist/views/assets/admin.css

  6. build:js

    assets-source/*.js → dist/views/assets/*.js

  7. wrangler

    src/index.ts + dictionary → dist/worker/index.js (on deploy or local workerd)

Views must be built before CSS: Tailwind reads the list of enabled features that build:views writes, so it only keeps the classes those views use.
