# Durable contributor deletion — 4 November 2026

This continues W4b/R3 after contributor duplication on `e882916`. Single `DELETE /__cms/pages/:id`, batch `DELETE /__cms/pages/batch` and collection `DELETE /__cms/pages/children` now use the shared guarded host lifecycle transaction through a neutral service adapter. Local trash moves and durable evidence commit together. This completes these local contributor deletion routes; external withdrawal, ingestion and general recovery remain open.

## Current credential and selection

The route captures a deletion-specific proof before parsing mutation input. Stable registry ID/UUID, enabled URL binding, stored/resolved/inbound dedicated credential, exact manifest pin, declared and currently approved write scopes, classification generation and registry lifecycle receipt witness are checked at execution and completion. A read approval cannot authorize a delete; an explicitly approved wildcard retains its existing meaning. No CMS user or session is manufactured. The principal is `plugin:<registry UUID>` with null user/roles/session; acting-user headers remain explicitly unverified assertions.

Single/batch selection uses positive safe integer IDs, deduplicates IDs, skips missing batch rows, and preserves the 100 input-item cap before deduplication. Invalid IDs now fail explicitly rather than being silently dropped. A missing single page returns 404; empty batch/collection calls are guarded no-ops without false mutation receipts. A mixed forbidden batch refuses the whole operation before any allowed prefix changes. Named scope refusals require an exact classified denial receipt; evidence failure returns unavailable.

Children retain parent or pointer selection and the 1,000-page request cap. The request freezes up to 1,001 ordered identities (1,000 targets plus look-ahead), full matching count, associated tag identities/taxonomies and retained floors. Every chunk verifies the remaining original selection and count, subtracting only its own acknowledged/transactional removals. Newly matching rows, reparenting, changed identities/types, changed associations/protection or revoked authority stop the next affected chunk. Each chunk reads and guards its full current page/history/link snapshot before moving it. The request does not freeze all body/history versions at initial selection; it accepts each chunk's version only through its exact transaction-bound snapshot.

Selection and source/metadata audit writes are awaited before mutation. Effective evidence classification includes current table/type/taxonomy policy, retained page floors and service classification. Evidence excludes names, slugs, lect/history bodies, selectors, credentials and private configuration; selector fingerprints and internal identities supply correlation.

## Atomic local outcome

A guarded `page.delete.intent` records the operation ID, bounded target identities and selection fingerprint before any trash move. Each chunk rechecks that intent. The shared core lifecycle writer preserves its page, version, link, destination-collision, parent and sensitivity checks. It copies complete page/history/tag state, preserves original source-parent references, then removes draft rows. Deleting only a parent leaves unselected draft children in place. It does not purge held records or bypass W12 hold/erasure controls.

Each local transaction includes one exact `page.delete` receipt per moved page and a `page.delete.chunk` manifest with the source/history/link identities, original parent references, chunk index, acknowledged boundaries and request-completion flag. Exact business postconditions and every receipt are checked after all writes, so ignored inserts, rewritten/deleted receipts and later receipt triggers cannot silently report a successful chunk. Existing host-user lifecycle attribution and job leases remain in the shared writer. The service path permits only bounded trash moves, never implicit restore/purge authority.

Storage and manifests are bounded: at most 100 pages per transaction, 1,000 targets per child request, and the shared 5,000-row / 1 MB snapshot limits. Missing trash storage and oversized snapshots fail closed before draft deletion; there is no fallback to a destructive hard delete. These checks add local reads/guards; they are not evidence of free-plan or staging capacity acceptance. No schema migration is introduced.

## Partial, uncertain and external effects

Progress advances only after D1 acknowledges a chunk. An error result records the operation and acknowledged count; a known SQLite rollback or failure before a business batch distinguishes `not_committed`/`prefix_committed` from an unknown unacknowledged chunk. A lost response retains whatever content and receipts committed, returns unavailable and never replays the chunk or asserts rollback. Error evidence itself is best effort during an outage and cannot substitute for inspecting exact receipts/current state.

Repeated HTTP requests remain separate operations. A subsequent children request selects what remains and may include newly matching records; it is not an idempotent retry or an authorization to replay an uncertain deletion. Durable lookup/reconciliation and request identity remain R5 work.

Hooks run separately after acknowledged local success, use the verified service actor and suppress the old duplicate best-effort mutation event. Single/batch publication withdrawal keeps its existing external behavior; children continue not to withdraw individual publications. The local receipt explicitly records withdrawal as a separate effect or not requested. It never certifies remote withdrawal or hook delivery. Their durable delivery/recovery outcomes remain R4; an external failure cannot roll back an acknowledged local trash move.
