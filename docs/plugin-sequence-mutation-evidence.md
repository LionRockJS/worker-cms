This continues W4b/R3 after the [automatic identity/state slice](plugin-state-lifecycle-mutation-evidence.md) on `4cc92b7b`. `POST /__cms/sequences/:key/next` now commits each counter advance and its exact classified `plugin.sequence.advance` receipt together in private D1. R3 and W4b remain open.

## Transaction-time allocation

An advance cannot use the state writer's Worker-side value/catalogue snapshot: simultaneous callers would all observe the same value and reject each other's ordinary increments. Instead, the sequence writer plans the allocation **inside the serialized D1 batch**. Its audit insert selects the current counter and records `value_before`, `value_after = value_before + 1`, preserved/planned creation time and the transaction's advance time. The complete receipt envelope and that plan are verified against the still-current counter before any counter write. The counter upsert uses precisely the planned value/timestamps from that operation's receipt and returns the assigned value with `RETURNING`.

Final checks compare the complete receipt with the resulting counter, including the exact increment, creation time and update time, then revalidate authority and policy. An ignored business write or missing/ignored/rewritten receipt cannot commit success. Counter/receipt/pin/credential/policy rewrites injected by the tested triggers roll back the entire batch. Timestamp verification uses the saved transaction clock so statements crossing a second boundary do not invent a conflict. The shared core factory accepts only trusted producer SQL projections and bound values; it imports no optional feature or sequence schema.

This is a selected-counter invariant, not a snapshot of every unrelated counter's contents. The production SQL selects and modifies only the authenticated namespace/key. No extra ledger, schema migration, counter reset or new background job is introduced. The raw DB-only `nextPluginSequence` compatibility/fixture helper has no remaining production caller and does not establish this evidence contract.

## Current credential authority and private receipts

Immediately after API authentication, `sequence-evidence.ts` captures the current registry row, stable ID/UUID, exact identity pin, dedicated stored credential and classification generation. Both the resolved and inbound credentials must match the stored dedicated credential with the timing-safe helper. Current authority is checked at transaction admission, again after planning and at completion. Disable, credential rotation, repin, unregister or replacement registration cannot rebind an old request to a new authority. If an advance wins before unregister, its number remains consumed; counters retain the existing intentional survive-unregister behavior and existing explicit identity-move semantics.

The actor is `plugin:<registry UUID>` with null user, roles and CMS session. A safe positive `x-acting-user-id` is only `asserted_user_id` with `acting_user_verified:false`; unsafe assertions are marked without retaining the raw header. The plugin credential does not establish a CMS user's session or role.

Targets use `<registry UUID>:sequence:<SHA-256 key fingerprint>`. Detail retains an operation UUID, registry ID, identity/key fingerprints, fixed principal/field/increment metadata, actual before/after numbers, timestamps and classification-policy version. These events use `admin_config` retention. Raw sequence keys, manifest IDs, labels, URLs/query strings, configuration and credentials are excluded. Fingerprints support reconciliation and are not an anonymization guarantee.

The highest effective classification across registry, identity approvals, sequence table and plugin scope applies, including retained floors. Protected authority/counter-source evidence is awaited using private metadata; strict pending reads flush before writing. The counter source is evaluated within the batch rather than copied as a potentially stale number into Worker memory. GET retains its separate established `sequence.read` contract, including existing raw key metadata and contributor read attribution. The mutation no longer adds a redundant legacy read announcement after commit; this slice does not claim global read-path reconciliation.

## Limits and uncertain results

Existing key syntax and successful `{ key, value }` responses remain. Twenty concurrent calls can allocate twenty distinct contiguous numbers with twenty corresponding receipts. Existing counters, including a legacy zero-valued row, remain advanceable at the 1,000-key cap. New keys at the observed cap require an exact classified denied receipt with `sequence_key_limit` before returning the existing 409 response. A transaction-time count/existence guard closes the final-slot race; a raced admission or changed refusal decision may return 503, and a later request observes the current cap. Failed denial evidence also returns 503 rather than a normal 409.

Existing counter values must be nonnegative SQLite integers below JavaScript's safe-integer maximum before advancing. The final safe integer may be issued once; exhausted, negative, fractional or malformed legacy counters refuse with 503 and no successful advance receipt. No reset, repair or renumbering is attempted.

Guarded failures use `service_mutation_unavailable`, 503/no-store, and attempt coarse incomplete health evidence without source values. No automatic mutation replay or compensation occurs. A lost acknowledgment may follow a complete counter/receipt commit; that number stays consumed. A new request advances again and may leave a visible numbering gap. Operation IDs are correlation metadata, not client retry tokens. Durable receipt lookup, controlled retry and uncertain-result recovery remain R5.

Missing security/counter/audit/version schema and malformed classification refuse. Registry/pin snapshots retain the shared bounded-snapshot limits. This writer does not load a namespace catalogue or unrelated opaque state values; database count/query capacity and deployed concurrency still require R6 acceptance.
