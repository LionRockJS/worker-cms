# W4b durable mutation evidence

**Status: local identity/session/access-policy foundations and the draft-editor content/history and weights/reorder/local-bulk and taxonomy/tag slices are implemented. W4b remains open with [six remaining work packages](w4b-remaining-scope-2026-11-02.md); regulated writes remain blocked.** This is repository evidence, not deployment acceptance or a standards-compliance finding.

The existing audit envelope supplies the actor, request and event metadata. The new mutation evidence builder creates an audit write and a guard for the exact event. The covered D1 mutations and those statements run in one batch, with additional postconditions for the business state. A failed statement or invariant aborts the batch; a connection failure after a possible commit can leave an ambiguous outcome, so an operator must reconcile current state and the corresponding event before retrying.

| Covered operation | Evidence and safeguards |
|---|---|
| Assign or update a classification | `data_class.set` carries the submitted class and actor/request context. The policy, sensitivity-floor changes and event share the transaction; the free-text note is excluded from the event. |
| Create a role | `role.create` is attributed and classified. The free-text label is excluded. Existing orphaned permission rows cause refusal rather than silently becoming grants. |
| Replace role permissions | `role.update` records the prior stored grants, the complete sorted new grant set and whether the role was managed. The observed role/grant snapshot is rechecked inside the transaction. Unmanaged built-ins retain their code-defined defaults. |
| Delete a custom role | `role.delete` records its prior grants and an operation ID. Each affected user receives a linked `user.roles` event with exact before/after roles; checks compare the affected set, evidence and final roles. Built-in role deletion is refused. |
| Assign user roles | `user.roles` records the internal target ID and before/after roles. The transaction rechecks the observed role and the last-administrator condition. |
| Delete a user | `user.delete`, the user, sessions and linked identities are handled in one batch. The event retains the prior role and internal ID, not the user's email. |
| Link an OAuth identity | `user.oauth-link` commits with the new identity; its target is the generated internal identity ID. Actor, current roles, verified provider and the authorizing CMS session are retained. Existing links are validated without another insert/event. |
| Refresh a profile from OAuth | `user.oauth-profile` commits with changed email/name/avatar fields, recording field names rather than values. Account state, ownership and email-collision decisions are rechecked; unchanged profiles do not generate mutation events. |
| Edit own display name | `profile.update` and the display-name update share a guarded transaction, with current session/account checks and field-name-only evidence. Unchanged names do not produce another mutation. |
| Disconnect own identity | Removal, any primary OAuth-key replacement and a complete outbox envelope commit together. Exact primary-stream delivery retries independently, so a primary audit outage does not prevent eligible disconnection. At least one stored sign-in method remains. |
| Host authentication denials | Named OAuth/refresh/admission/rate-limit and shared permission refusals await exact primary evidence or a verified complete outbox receipt. Both-store failure stays refused as 503; anonymous claims and raw provider/URL/credential data are excluded. See the [denial record](authentication-denial-evidence.md). |
| Session lifecycle | Creation/sign-in, rotation and access-only grace have durable primary evidence; logout/direct revocation and bounded cap/expiry cleanup have atomic outbox receipts. User deletion records its complete revoked-session set. See the [session record](session-lifecycle-evidence.md) for exact semantics. |
| Register an OAuth account | `user.create`, the account's initial viewer role and its provider identity commit in one batch, before issuing a session. The verified provider is identified by `acting_via`; the actor and target use the generated internal user ID, resolved inside the transaction. Provider-supplied roles never become the initial role. |

Access-management events use the highest classification of the relevant tables. Invalid or unavailable classification refuses the operation, and pending strict protected-read evidence is flushed before mutation. Unsafe or oversized legacy role/grant metadata is refused rather than copied into the audit trail; permission entries are limited to 256 characters and a recorded grant set to 32,768 UTF-8 JSON bytes. A failed or ambiguous transaction sends an incomplete coarse incident through the existing monitoring path when enabled, without claiming which statement failed or whether a commit occurred.

The covered deletion is tested with 205 synthetic users, but production-scale cost and D1 limits still require deployment-specific assessment. A transaction that exceeds its limits must be treated as unsuccessful or ambiguous until reconciled.

## OAuth registration continuation — 2 November 2026

`src/core/auth/registration.ts` now owns the new-account transaction, using the shared core audit envelope even without the optional users/roles administration feature. Its event takes the highest effective classification of `users`, `user_oauth_identities`, `roles` and `role_permissions`. Failed/invalid classification refuses registration. The event excludes email, name, avatar, provider subject, tokens and authorization code; it retains only provider, initial role and internal identifiers with request attribution. No CMS session exists at creation time.

Transaction guards reject ignored user/identity/audit inserts, removed or rewritten evidence, changed profile/role fields and missing or mismatched identities. Existing identity collisions are not adopted. Registration failure returns 503/no-store before issuing access/refresh cookies or creating a session, and uses the existing incomplete coarse health incident when monitoring is enabled. A connection failure after commit does not mean rollback: the callback does not automatically retry; the retained account and event can be reconciled, and a later verified sign-in follows the existing-account path without another creation event. This is not a general idempotency or session-evidence implementation.

The focused registration suite has 23 regressions for classified attribution/privacy, least-privilege provisioning, transaction faults, conflicts, post-commit uncertainty, monitoring payloads, existing login behavior and registration allowlists. Integrated validation passed 1,390 tests across 69 files, plus build, TypeScript, profile, boundary and generated consistency checks. Classification is resolved before the transaction, as in the earlier access-management slice; atomic policy-version checks and deployment acceptance remain outstanding.

## Existing-account OAuth continuation — 2 November 2026

The existing-account callback now uses `src/core/auth/oauth-account.ts` for explicit identity linking and provider profile refresh. Each actual mutation and its exact audit row share a guarded D1 batch. Evidence uses the highest effective class of users, identities, roles, grants and sessions. Unsafe legacy role metadata or unavailable/invalid classification refuses the operation. The core implementation does not require the optional users/roles administration feature.

Linking requires a verified provider and a CMS session for the same account. `oauth-link-session.ts` checks the session at OAuth start/callback and again before and after the insert/evidence statements. Those transaction checks cover token expiry, session revocation, session/absolute expiry and, for refresh-token authority, idle expiry and current/previous token hash with the existing rotation grace. Refresh JWT subjects must own their session. Resolving this authority neither rotates tokens nor renews the old session. The callback still issues its new login session separately after the account batch succeeds; durable session lifecycle evidence remains outstanding.

Profile refresh preserves the existing role and CMS-owned display name, seeds a missing name using the prior SQLite space-trimming semantics, and keeps the existing email if another account owns the provider email. The account snapshot, identity ownership and collision decision are guarded inside the transaction. A concurrent role/profile change, identity reassignment/removal or changed collision decision refuses the stale operation. Legacy primary OAuth keys remain valid when no conflicting identity row exists; malformed linked metadata cannot use that fallback.

Events retain request context, internal IDs, provider, affected field names and safe current roles. They exclude email/name/avatar values, provider subject, tokens and authorization code. Guard failures, ignored writes, removed/rewritten evidence and inconsistent final account/identity/session state abort the entire batch. Failed or uncertain callbacks return 503/no-store before creating another session or issuing access/refresh cookies, using the existing incomplete coarse health incident when enabled. Previously issued sessions are not cleared by that response.

A lost commit acknowledgment is not treated as proof of rollback and is not automatically replayed. A later verified callback validates an existing link or unchanged profile without repeating the mutation/event. This narrow state-based retry behavior is not a durable general operation-id/reconciliation system. Classification is still resolved before the transaction; this increment does not implement atomic policy-version validation or close W4b as a whole.

Validation: 61 focused regressions cover classified/private evidence, Google/Eventuai profile behavior, no-op callbacks, transaction failures, session/refresh checks, concurrent ownership/role/email changes, uncertain commits and monitoring privacy. Five affected suites passed 394 tests. The integrated serial run passed 1,451 tests across 70 files; build, TypeScript, profile, boundary, generated consistency and diff whitespace checks passed. These are local results, not deployed acceptance.

## Self-service profile and disconnection continuation — 2 November 2026

Verified that the previous existing-account OAuth callback work is still present, then continued the related self-service mutations. `src/core/auth/self-profile.ts` now implements display-name edits and identity disconnection independently of optional administration features. Display-name changes preserve all other profile/role fields and commit with classified `profile.update` evidence; ignored/failed audit writes, changed account state or revoked/expired authorizing sessions abort the batch. No-op submissions validate without another mutation event. Regulated business-write containment still denies profile edits.

Identity disconnection is a containment path, including in the regulated profile. The current session, account/role snapshot and complete stored identity set are checked inside its transaction. A primary-key replacement and removal are atomic, and final invariants protect the surviving sign-in method, current session and exact evidence. Unknown classification is recorded conservatively as PHI with an explicit marker; unsafe roles are omitted with an explicit marker. Evidence identifies internal user/identity/session IDs and any replacement identity ID without copying profile values or provider subjects.

To preserve disconnection during a primary audit outage, its complete event envelope commits in a new core D1 outbox, then attempts delivery to the existing audit stream. The bounded core maintenance sweep runs before regulated readiness and does not depend on the audit UI. It uses stable event IDs, exact receipt comparisons, transactional removal, exponential backoff, an eight-attempt ceiling and retained exhausted evidence with backlog/monitoring visibility. This is a narrow durable D1 revocation receipt, not an external cross-service transaction or a completed general operation-id/recovery system. Lost mutation commit acknowledgment requires state reconciliation; delivery never replays a disconnection.

Existing installations need the additive [outbox upgrade](../migrations/manual/2026-11-02_audit_mutation_outbox.sql); the generated fresh-install baseline and regulated readiness check include its table/index. No production migration, scheduler configuration or deployment was performed. The [outbox runbook](audit-mutation-outbox.md) covers rollout, restricted backlog inspection, exhausted-event review/retry and remaining operating evidence. Classification remains pre-transaction; W4b is not closed by this increment.
