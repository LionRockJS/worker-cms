# Durable automatic plugin identity claims and state lifecycle — 3 November 2026

This continues W4b/R3 after the [local financial/configuration slice](financial-administration-mutation-evidence.md) on `cb77dcd`. Automatic first-use identity claims and the production `PUT`/`DELETE /__cms/state/:key` paths now commit their state and exact classified receipts in one private-D1 transaction. R3 and W4b remain open.

## Automatic host identity claims

`src/features/plugins/registry.ts` now calls `automatic-identity-evidence.ts` instead of the unaudited DB-only `claimIdentity` primitive. A bounded manifest observed through the existing resolver/manifest cache supplies the candidate identity. The observed registry ID, UUID, URL and dedicated credential must still match the enabled host registration after the exchange. Current full registry metadata is then captured and guarded through commit. Cosmetic/configuration updates during the public manifest exchange can be captured afresh; a changed security binding cannot be adopted by that old observation.

The enabled host registration authorizes automatic trust-on-first-use. The actor is the host mechanism `service:plugin-registry`, with null user, roles and session. This is neither administrator reapproval nor proof of an inbound plugin caller's credential. A request with a bad plugin secret can still trigger ordinary host manifest resolution; the eventual API authentication remains separate. Caller-supplied user/session/role headers cannot become the claim actor. HTTP request correlation is carried through neutral request-local metadata; off-request calls retain null request fields.

The selected registry row, identity ownership scope (row ID or candidate manifest ID), classification generation and final pin are guarded. One actual new claim produces `plugin.identity.claim`, targeted at the stable registry UUID, with the numeric registry ID, operation correlation, fixed `first_resolution` mode, and identity/observed-manifest fingerprints. Labels, URLs/query strings, configuration, credentials, raw manifest IDs and other remote manifest values are excluded. The highest effective registry/identity table and inspected plugin-scope classification applies, including retained floors.

The pin insert, exact receipt, creation/update-time bounds and final registry/identity/policy assertions share one transaction. Missing/ignored/rewritten business or receipt statements, trigger-induced pin/registry/policy changes and absent security/audit schema refuse. Existing or competing pins are validated without a false new-claim event. An identity owned by another row is never reassigned by this producer.

Concurrent first use is handled conservatively. A failed D1 batch identified as a SQLite statement failure has rolled back; the helper may **only read and validate** an already committed matching winner under its original registry/policy snapshot. It never retries the business insert. Transport or lost-acknowledgment errors remain unavailable even if a pin is visible. A later resolution validates the committed pin without duplicating its event. This preserves concurrent first-use behavior without weakening exact receipt checks or pretending that an uncertain response proves rollback.

This is an identity binding, not a new capability grant, remote authenticity guarantee or orphan-remediation policy. Existing manifest TTL behavior remains. Explicit reapproval and unregister cleanup retain their preceding contracts. Legacy orphan namespaces and direct-operator history still need R6 reconciliation; sequence counters intentionally retained on unregister are not silently deleted by an automatic claim. Regulated mode continues to prohibit new automatic claims while allowing existing pins to resolve.

## Credential-bound state mutations

The resolver exposes the internal registry ID/UUID to trusted server code. `state-evidence.ts` captures this registration, full registry metadata, the exact identity pin and current classification generation immediately after API credential authentication and **before parsing the request body**. The dedicated stored credential is compared with both the resolved credential and request header using the existing timing-safe helper. The environment-wide legacy secret is not an inbound fallback.

Every mutation rechecks this captured registration/pin/credential inside the same batch as its selected state change and receipt, then checks again at completion. Disabling, rotating, unregistering, replacing a registry row or repinning during an in-flight request makes that old request unavailable. If audited unregister cleanup commits first, a subsequent old state PUT cannot recreate the removed namespace. If a state write wins first, the preceding unregister writer's own snapshot checks refuse stale cleanup. This does not claim that every other unmigrated plugin writer has the same lifecycle checks.

The authenticated principal is the credential-bearing plugin registration, recorded as `plugin:<registry UUID>` with null user, roles and CMS session. A safe positive `x-acting-user-id` is retained only as `asserted_user_id` with `acting_user_verified:false`; malformed/unsafe assertions receive an unrecordable marker without their raw value. The header cannot supply a CMS session, roles, capabilities or verified user attribution. No HTTP user is fabricated for service work.

## Point-state transaction and private evidence

| Operation | Durable result |
|---|---|
| New key PUT | Entry creation and exact `plugin.state.put`. |
| Existing changed key PUT | Selected value/update timestamp and exact `plugin.state.put`, preserving creation metadata. |
| Existing key DELETE | Exact selected removal and `plugin.state.delete`. |
| Unchanged PUT / missing DELETE | Current authority, policy and captured state validation; no timestamp write or false mutation event. |
| New key at the namespace cap | Exact classified denied `plugin.state.put` receipt with fixed `state_key_limit`, then 409; no state change. |

Success/denial targets use `<registry UUID>:state:<SHA-256 key fingerprint>`. Receipts retain the registry ID, operation and classification generation, fixed authenticated-principal marker, identity/key fingerprints and affected field names. They exclude raw keys, opaque values, value hashes, labels, URLs, configuration and credentials. These host relationship/configuration events use `admin_config` retention. Fingerprints are reconciliation identifiers, not an anonymization guarantee.

The exact selected entry and the namespace's key/creation/update-time catalogue are captured and guarded. Opaque values belonging to other keys are not loaded into this point writer. This preserves support for the existing 100-key namespace with individually valid values even when their combined bodies exceed one megabyte. The catalogue protects the key-count decision and relevant metadata; it does not assert a byte-for-byte snapshot of every unrelated value. Selected value, complete expected key/timestamp catalogue, preserved creation time and transaction-time update bounds are verified after the write. Other namespaces remain untouched by the production SQL.

Key syntax, opaque JSON storage, UTF-8 64-KiB value bounds, the 100-key cap and stable successful response bodies remain. Only a new key is refused at the cap; overwrites remain available. Concurrent last-slot admissions cannot exceed the cap through these writers: stale catalogues refuse, and a later new request records the cap denial. An unavailable cap receipt returns 503 rather than a normal 409. This service-principal denial uses an exact primary receipt; the existing user-auth denial outbox is not falsely reused for a plugin credential principal.

Protected authority/state source reads are awaited with hashed key metadata, and pending strict request reads are flushed before writing. Effective classification includes the plugin and registry/identity/state tables and is checked against the same policy generation at admission and completion. Missing state/security/version/audit schema, unsafe source snapshots and ignored or rewritten writes refuse with no partial state mutation. GET/list retain their established separate read-audit contracts, including their existing key metadata; this increment does not claim global read-path privacy reconciliation.

## Bounds, outcomes and remaining scope

Neutral snapshot helpers now accept a database-only context, so off-request services need no fabricated Hono context. SQL snapshots remain bounded to 5,000 rows and 1,000,000 UTF-8 JSON bytes before returning values; the selected state value retains its stricter API bound. Oversized legacy catalogues/selected entries require reviewed remediation. The earlier unregister/reapproval cleanup writers retain their own aggregate snapshot bounds; this point writer does not make every large namespace cleanup unbounded.

Guarded failures return `service_mutation_unavailable`, 503/no-store, and attempt coarse incomplete health evidence without source values. No automatic state mutation replay or compensation is added. A lost acknowledgment may follow a complete state/receipt commit. Identical later PUTs or absent DELETEs have narrow state-based no-op behavior, but a new request is not a durable operation-ID retry. Receipt lookup, controlled retries and reconciliation remain R5.

A production-call inventory found no remaining calls to raw `claimIdentity`, `putPluginState` or `deletePluginState` after these routes moved. Those DB-only compatibility/fixture helpers do not establish the new evidence/authority contract. Direct SQL, imports and migration operators remain R6. Sequence advances were not converted by this slice; the subsequent [sequence-counter record](plugin-sequence-mutation-evidence.md) documents their transaction-time receipts and concurrency/authority checks. Other contributor page/content writers, charge/usage/billing and jobs remain R3, with external effects/recovery in R4/R5.

No schema migration, production mutation, push, deployment or compliance sign-off occurs in this increment. Regulated business writes remain blocked. Four packages R3–R6 remain open, still provisionally **18–32 engineering person-days** plus external acceptance time; see the [scope register](w4b-remaining-scope-2026-11-02.md).
